# JDK 25 results

Builder baseline [`c0acd3a`](https://github.com/DanielThomas/protobuf/commit/c0acd3a8f5aedaa6705530b9704c2af527f51575) versus parser [`01935fc`](https://github.com/DanielThomas/protobuf/commit/01935fc6f86dca758e2547018ed3925d7e6dea72), using benchmark revision [`0c313de`](https://github.com/DanielThomas/protobuf/commit/0c313dec156cb6cbea2d36ee557d85190c8ead7c).

This repeats the [JDK 8 run](jdk8-handoff-78f185ad.md) on the same host with the same javac 8-compiled jars, changing the execution JVM to Zulu OpenJDK 25.0.5+8-LTS. These are Java 8 class files running on JDK 25, not a Java 25-targeted rebuild.

All 1,168 public forks passed. All 73 public binary inputs are included below. Text-format and unknown-field workloads passed their input checks but were not timed. The representative private request was measured separately and its aggregate result is in [PR #1](https://github.com/DanielThomas/protobuf/pull/1).

| Measurement | Lower | Higher | Unresolved |
| --- | ---: | ---: | ---: |
| Parse time | 60 | 7 | 6 |
| Allocation | 55 | 9 | 9 |

Lower is better for both. Parse time is the mean of five timing forks, in ns/op. Allocation is the mean of three separate allocation forks, in B/op. Deltas are parser minus builder +/- the paired 95% confidence margin, rounded to one decimal place. Intervals spanning zero are unresolved, not evidence of equivalence. These are exploratory two-sided Student t intervals without multiplicity correction, with four degrees of freedom for time and two for allocation.

## Configuration

- Bare-metal Intel Xeon 6975P-C, 96 physical cores over three NUMA nodes. Zulu 25.0.5+8-LTS for execution, javac 8u512-b08 for compilation with `-g -parameters -proc:none`.
- Same 74-lane schedule as the JDK 8 run, including the separately reported private request. One thread and distinct physical core per input, fixed local NUMA memory binding. SMT siblings are unused by benchmark forks, but cores are not OS-isolated.
- Measured JVM flags: `-XX:ActiveProcessorCount=1 -XX:+UseSerialGC -Xms2g -Xmx2g -XX:+AlwaysPreTouch`. Compact object headers and JVM NUMA allocation are disabled by default. The same CPU and memory binding applies to both variants.
- Five paired timing forks per variant/input, three one-second warmups and five one-second measurements. No profiler, agent, forced inlining or compiler logging.
- Three separate paired allocation forks per variant/input, three one-second warmups and measurements. The unchanged worker-thread allocation-counter profiler and `gc:alloc=false` are used. The worker profiler remains outside the public target.
- All 740 timing forks finished before any of the 444 allocation forks began. All 1,184 forks passed. No retries, discarded forks or pooling with earlier measurements.
- Variant order alternates by round and starting order reverses across inputs. A barrier separates each 74-fork wave. CPU affinity and heap placement are checked during startup or early warmup, with no further process-file reads during measurement.
- Identical jars and public input hashes to the JDK 8 run. All 385 benchmark/JMH classes and metadata entries remain byte-identical across variants.

The [benchmark README](../README.md#compare-revisions) describes building and alternating paired forks. For each timing fork, using the appropriate baseline or candidate jar:

```sh
numactl --physcpubind="$CPU" --membind="$NODE" \
  "$JDK25_HOME/bin/java" -jar "$JAR" \
  'com.google.protobuf.benchmarks.ParseBenchmark.parse$' \
  -p input="$INPUT" -t 1 -f 1 -wi 3 -i 5 -w 1s -r 1s \
  -bm avgt -tu ns -foe true \
  -jvm "$JDK25_HOME/bin/java" \
  -jvmArgs '-XX:ActiveProcessorCount=1 -XX:+UseSerialGC -Xms2g -Xmx2g -XX:+AlwaysPreTouch' \
  -rf json -rff "$RESULT"
```

No new compilation diagnostics were collected. Earlier evidence of interpreted decoding loops is historical, not new JDK 25 compilation evidence. The known nested inactive-oneof-history and failed UTF-8 unfinished-oneof correctness gaps are unchanged and separate from this performance evaluation.
